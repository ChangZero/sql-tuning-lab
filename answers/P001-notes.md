# P001 해설

## 핵심
`SUBSTR(o.ord_dt, 1, 6) = '201203'` — **인덱스 컬럼에 함수를 씌우면 인덱스를 못 탄다.**
`ORD_X01(ORD_DT, ORD_HMS)` 은 `ORD_DT` 원본 값으로 정렬돼 있는데, 옵티마이저는
`SUBSTR(ORD_DT,1,6)` 의 값이 인덱스 상에서 어디 있는지 알 수 없다. 결국 풀스캔.

`ORD_DT` 가 `VARCHAR2(8)` 의 `YYYYMMDD` 이므로 **문자열 정렬 순서 = 날짜 순서**다.
따라서 컬럼을 가공하지 않고 범위 조건으로 바꿀 수 있다:

```
where o.ord_dt between '20120301' and '20120331'
```

## 기준 성능
| | Buffers | A-Time | 접근 경로 |
|---|---|---|---|
| 원본 | 333,000 | 3.12s | TABLE ACCESS FULL ORD |
| 모범답안 | **16,284** | 0.17s | INDEX RANGE SCAN ORD_X01 → TABLE ACCESS BY INDEX ROWID |

약 20배 개선.

## 부수적 관찰 (심화 질문용)
모범답안 실행계획에서 Id 11 의 **E-Rows 81,527 vs A-Rows 625,000** — 8배 과소추정.
`ORD_DT` 가 문자열이라 옵티마이저의 범위 카디널리티 추정이 부정확하다.
이번엔 계획이 우연히 맞았지만, 조인이 더 복잡해지면 이 오추정이 조인 순서를 망가뜨린다.
→ Lv4~5 에서 다룰 주제.

## 흔한 오답
| 제출 | 문제 |
|---|---|
| `to_char(to_date(ord_dt,'YYYYMMDD'),'YYYYMM') = '201203'` | 여전히 컬럼 가공. 풀스캔 그대로 |
| `ord_dt like '201203%'` | 인덱스는 타지만 선행 와일드카드가 아니라 동작은 함. BETWEEN 과 성능 동일 — 정답 처리 |
| `/*+ index(o ord_x01) */` 만 추가 | 힌트로 강제해도 `SUBSTR` 조건은 필터로만 쓰여 인덱스 풀스캔이 됨. 오히려 더 느릴 수 있음 |
| `ord_dt >= '20120301' and ord_dt < '20120401'` | 정답. BETWEEN 과 동일 |
| ANSI `INNER JOIN` 사용 | 결과가 맞아도 문법 위반 지적 |
