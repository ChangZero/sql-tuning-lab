# 출제·채점 워크플로우

전제: [docs/SCHEMA.md](../../../docs/SCHEMA.md), [docs/ORACLE-SYNTAX.md](../../../docs/ORACLE-SYNTAX.md),
[docs/TUNING-PLAYBOOK.md](../../../docs/TUNING-PLAYBOOK.md) 를 읽고 시작한다.

## A. 출제

1. **난이도·주제 결정**
   - 사용자가 지정했으면 따른다. 지정이 없으면 `progress.md` 의 최근 이력을 보고,
     최근에 틀린 주제를 한 단계 쉽게 다시 내거나, 통과한 주제의 다음 단계로 올린다.
   - 이력이 없으면 Lv1 부터 시작한다.

2. **문제를 만들기 전에 정답 SQL을 먼저 작성하고 실제로 실행한다.**
   `./bin/osql -c "..."` 로 돌려서 **결과가 0건이 아니고, 행 수가 화면에 담길 만한지**(보통 50행 이하)
   확인한다. 이 검증 없이 출제하지 않는다. 자주 내는 실수:
   - 데이터 범위 밖 날짜 (20120101~20131231 만 존재)
   - 결과가 수만 행이라 확인 불가
   - 튜닝 문제인데 기준 SQL이 180초 타임아웃에 걸림

3. **튜닝 문제라면** 느린 원본 SQL과 목표 SQL을 둘 다 `./bin/oplan` 으로 돌려
   Buffers 차이가 실제로 유의미한지(최소 3배 이상) 확인한다. 차이가 안 나면 문제를 바꾼다.

4. **파일 작성 — 문제는 반드시 별도 파일로 만든다.** 채팅에 문제 본문을 길게 쓰지 않는다.
   - `problems/PNNN-slug.md` — 아래 양식. 번호는 기존 최대값+1, slug 는 영문 소문자-하이픈.
   - `answers/PNNN.sql` — 모범답안 SQL 한 개 (세미콜론 없이, 주석 없이. ocheck 가 그대로 실행한다)
   - `answers/PNNN-notes.md` — 해설, 기준 Buffers, 흔한 오답과 그 이유
   - `attempts/PNNN/t1.sql` — **빈 제출 스텁.** 문제마다 `attempts/PNNN/` 폴더를 만들고 그 안에 둔다.
     사용자가 여기에 바로 SQL 을 쓰면 되게 미리 만들어 둔다.
     주석 헤더에 문제 제목·문제 파일 경로·출력 컬럼과 순서·정렬·결과 행 수·제약·`/grade PNNN` 을 적고,
     그 아래는 비워 둔다. 정답의 구조나 힌트가 될 구문은 쓰지 않는다.

     ```sql
     -- P001 / t1 — <제목>
     -- 문제: ../../problems/P001-shop-top10-tuning.md
     --
     -- 출력 컬럼: SHOP_NM, ORD_CNT   (이 순서)
     -- 정렬     : ORD_CNT DESC, SHOP_NM ASC
     -- 결과     : 10행
     -- 제약     : 오라클 전용 문법(ANSI 조인 금지) / <문제별 제약>
     --
     -- 아래에 SQL 한 개만 쓴다. 끝에 세미콜론 없이, SQL 중간에 빈 줄을 넣지 않는다.
     -- 다 썼으면  /grade P001     (다시 풀 때는 같은 폴더에 t2.sql 로 복사해서)
     ```

5. **문제 파일은 그것만 읽고 풀 수 있어야 한다.**
   `docs/SCHEMA.md` 를 다시 뒤지게 만들지 말고, 그 문제에 필요한 정보를 문제 파일 안에 옮겨 적는다.
   - 쓰이는 **테이블별 컬럼**(문제에 관련된 것만) + 타입 + 건수
   - 그 테이블의 **인덱스 구성** (컬럼 순서 그대로). 튜닝 문제면 클러스터링 팩터·파티션 키까지
   - **조인 관계** (`ORD.SHOP_NO = SHOP.SHOP_NO` 처럼 명시)
   - 데이터 범위(20120101~20131231), 값 분포나 코드값처럼 조건을 쓰려면 알아야 하는 것
   - **출력 컬럼·컬럼 순서·정렬 기준**, 그리고 2단계에서 실측한 **정답 행 수**
   - 출력 예시 2~3행 (형식 확인용. 정답 전체를 붙이지 않는다)

6. **사용자에게는 문제 파일 경로 + 제출 스텁 경로 + 3~4줄 요약만 준다.**
   정답 파일(`answers/`) 경로는 언급해도 내용은 출력하지 않는다.

### 문제 양식
```markdown
# P001 — <제목>

- 난이도: Lv2
- 주제: 조인 / 분석함수 / 인덱스 / 파티션 / 계층질의 …
- 유형: 작성 | 튜닝 | 진단

## 요구사항
<무엇을 구하는지. 한두 문장으로 명확히.>

출력 컬럼: `SHOP_NM`, `ORD_CNT`, `RNK`  (이 순서)
정렬: `RNK` 오름차순
결과 행 수: 10행

## 참고 정보
**ORD** — 주문, 15,000,000 건
| 컬럼 | 타입 | 설명 |
|---|---|---|
| ORD_NO | NUMBER | PK |
| ORD_DT | VARCHAR2(8) | `YYYYMMDD` 문자열 (DATE 아님) |
| SHOP_NO | VARCHAR2(10) | → SHOP.SHOP_NO |

인덱스: `ORD_PK(ORD_NO)` UNIQUE, `ORD_X01(ORD_DT, ORD_HMS)`

**SHOP** — 매장, 200 건. `SHOP_NO`(PK), `SHOP_NM`

조인: `ORD.SHOP_NO = SHOP.SHOP_NO`
데이터 기간: `ORD_DT` 20120101 ~ 20131231

## 제약
- 오라클 전용 문법으로 작성한다 (ANSI 조인 금지)
- <문제별 제약: "분석함수 없이", "인덱스 추가 없이 SQL만 수정", "Buffers 5,000 이하" 등>

## (튜닝 문제일 때) 현재 SQL
```sql
<느린 SQL>
```
현재 실측: Buffers 412,883 / A-Time 00:00:08.2 → **목표: Buffers 5,000 이하**

## 출력 예시
```
SHOP_NM        ORD_CNT  RNK
-------------- -------  ---
강남점            4,812    1
...
```

## 생각해볼 것
<정답을 알려주지 않는 유도 질문 1~2개>

## 제출
`attempts/P001/t1.sql` (빈 스텁을 미리 만들어 뒀다) 에 SQL 을 쓴 뒤 `/grade P001`
채점 결과는 같은 폴더의 `t1-grade.md` 로 남는다.
```

## B. 채점

1. 제출 파일을 읽는다 (`attempts/PNNN/tN.sql`, N은 그 폴더 안 최대값).
   주석(`--`)과 빈 줄을 걷어내고 남는 게 없으면 **스텁이 아직 비어 있는 것**이다.
   채점 도구를 돌리지 말고 "아직 안 쓰셨다"고 알리고 멈춘다.
2. **문법 점검** — ANSI 조인, 타 DBMS 방언이 섞였는지 확인. 있으면 결과와 무관하게 지적한다.
3. **결과 검증** — `./bin/ocheck answers/PNNN.sql attempts/PNNN/tN.sql`
   (문제가 정렬을 요구했으면 `--ordered`)
4. **성능 측정** — `./bin/oplan attempts/PNNN/tN.sql` 과 `./bin/oplan answers/PNNN.sql`.
   둘 다 **두 번씩** 돌려 두 번째 값으로 비교한다 (첫 실행은 물리적 읽기 때문에 느리다).
5. **판정**
   | 판정 | 조건 |
   |---|---|
   | 정답 | 결과 일치 + Buffers 가 모범답안의 1.5배 이내 |
   | 정답·비효율 | 결과 일치 + Buffers 가 그보다 큼 |
   | 오답 | 결과 불일치 또는 에러 |
   | 문법 위반 | 위 판정과 별개로 병기 |
6. **피드백** — 실행계획 실측치를 근거로 제시한다. "느립니다" 같은 말 대신
   "Id 4 에서 Starts=49,667 로 NL 내측이 반복 수행됐고 Buffers 가 여기서 412K 중 390K 를 씀" 처럼 쓴다.
   틀렸으면 정답 SQL을 바로 주지 말고 **어디를 고쳐야 하는지만** 먼저 말한다.
   사용자가 요청하거나 2회 이상 실패한 뒤에 모범답안을 공개한다.
7. **채점 결과를 파일로 남긴다** — `attempts/PNNN/tN-grade.md`. 채팅에 쓴 피드백과 같은 내용을 담되,
   나중에 다시 읽을 수 있게 실측치를 그대로 적는다. 구성:
   - 머리말: 일자 / 제출 파일 링크 / 문제 파일 링크 / **판정**
   - `## 1. 문법` — 위반 여부
   - `## 2. 튜닝` — 원본 vs 제출 vs 모범답안 Buffers·A-Time 표, 실행계획 Id 별 근거
   - `## 3. 결과셋` — `ocheck` 출력 그대로 + 불일치 원인
   - `### 고칠 점` — 번호 매긴 목록. **모범답안 SQL 이나 핵심 구문은 쓰지 않는다**
   - `## 다음` — 다음 시도에서 무엇만 바꾸면 되는지
   재채점(`t2`, `t3`…)은 각각 별도 파일로 남기고 이전 파일은 지우지 않는다.
8. **`progress.md` 갱신** — 한 줄 추가: 날짜 / 문제·시도 / 주제 / 판정 / Buffers(제출 vs 기준) /
   채점 파일 링크 / 메모

## C. 힌트

정답 SQL 이나 핵심 구문을 절대 노출하지 않는다. 한 번에 한 단계만:
1단계 = 어느 테이블·인덱스를 봐야 하는지, 2단계 = 어떤 오라클 기능이 필요한지,
3단계 = 구조 스케치(구문 없이). 사용자가 더 달라고 하면 다음 단계로.

## 난이도 기준
| Lv | SQL 작성 | 튜닝 |
|---|---|---|
| 1 | 단일 테이블 조회, `WHERE`, `ORDER BY`, 기본 집계 | 실행계획 읽기, 인덱스 탔는지 판별 |
| 2 | 2~3 테이블 조인, `(+)` 아우터, 서브쿼리, `DECODE`/`NVL` | 인덱스 무력화 패턴(컬럼 가공, 선행컬럼 누락) 찾아 고치기 |
| 3 | 분석함수, 인라인 뷰, 스칼라 서브쿼리, `ROLLUP`/`GROUPING SETS` | 조인 방식 전환(NL↔Hash), 조인 순서, 클러스터링 팩터 |
| 4 | 계층질의, `PIVOT`, `KEEP DENSE_RANK`, 윈도우 프레임, `MERGE` | 파티션 프루닝, 부분범위 처리, Top-N, 인덱스 설계 |
| 5 | 복합 요구사항을 한 SQL로 (이력 테이블 + 분석함수 + 계층) | 커버링 인덱스 설계, 통계/카디널리티 오추정 진단, 병렬 |
