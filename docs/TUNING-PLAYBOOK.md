# 튜닝 진단 플레이북 — 이 스키마에서 반복해서 나오는 패턴

채점·해설할 때 이 순서로 근거를 댄다. 추측하지 말고 항상 `bin/oplan` 실측치를 먼저 본다.

## 1. 읽는 순서
1. **A-Rows vs E-Rows** — 한 자릿수 이상 벌어지면 통계/카디널리티 오추정. 조인 순서가 틀어진 원인이 대개 여기다.
2. **Starts × A-Rows** — NL 조인 내측의 `Starts` 가 크면 반복 수행 비용. Starts=1 인데 A-Rows 가 크면 한 방에 많이 읽은 것.
3. **Buffers** — 논리적 읽기. 이 스키마의 **1차 성능 지표**. 벽시계 시간은 버퍼 캐시 상태에 따라 흔들리지만 Buffers 는 재현된다.
4. **A-Time** — 어느 단계에서 시간이 튀는지. 자식 노드 시간은 부모에 누적됨에 유의.
5. **Pstart/Pstop** — 파티션 테이블이면 프루닝됐는지. `KEY` 나 `1-25` 가 보이면 프루닝 실패.

## 2. 자주 나오는 오답 패턴
| 증상 | 원인 | 처방 |
|---|---|---|
| `ORD_X01` 을 두고 `TABLE ACCESS FULL ORD` | `ORD_DT` 에 함수 적용 (`TO_DATE(ord_dt,...) = ...`), 또는 선행컬럼 누락 | 컬럼 가공 제거, 상수 쪽을 가공 |
| 인덱스는 탔는데 Buffers 가 수십만 | 테이블 랜덤 액세스 폭주 (CF 나쁨) | 커버링 인덱스, 또는 인덱스에서 걸러낸 뒤 조인 |
| `ORD_DT` 에 `LIKE '2012%'` | 문자열 컬럼이라 동작은 하나 범위가 큼 | `BETWEEN '20120101' AND '20121231'` |
| `UPPER_CASE` 컬럼에 `UPPER(col) = :v` | 함수 기반 인덱스 없음 → 인덱스 무력화 | 컬럼 그대로 비교하거나 FBI 생성 |
| 소량 마스터(ITEM 92건, SHOP 200건)에 NL 내측 인덱스 반복 | 해시 조인이 더 쌈 | `USE_HASH`, 또는 조인 순서 변경 |
| 파티션 테이블인데 `ORD_YM` 조건 없이 `ORD_DT` 만 | 프루닝 실패, 25개 파티션 전부 스캔 | 파티션 키 조건 추가 |
| 스칼라 서브쿼리가 행마다 반복 | 캐싱 실패 (입력값 카디널리티 큼) | 조인으로 전환하거나 인라인 뷰로 선집계 |
| `COUNT(*)` 인데 테이블 풀스캔 | 인덱스로 대체 가능 | NOT NULL 컬럼 인덱스 활용 |

## 3. 이 스키마 전용 실험 축
- **클러스터링 팩터**: 같은 SQL을 `ORD` 와 `ORD_RANDOM` 에 각각 날려 Buffers 비교 (CF 333K vs 15M)
- **파티션 전략**: `ORD_RANGE` / `ORD_LIST` / `ORD_LIST_HASH` 에 같은 조건 → Pstart/Pstop 과 Buffers 비교
- **조인 방식**: 같은 조인을 `USE_NL` / `USE_HASH` / `USE_MERGE` 힌트로 강제해 교차점 찾기
- **통계 유무**: `ORD_TEMP` 계열은 통계 없이 두고 동적 샘플링 동작 관찰

## 4. 측정 위생
- 첫 실행은 물리적 읽기 때문에 느리다. **같은 SQL을 두 번 실행한 뒤 두 번째 결과로 비교**한다.
- 비교 대상 SQL 둘 다 같은 조건에서 돌린다. 한쪽만 캐시가 데워진 상태로 비교하지 않는다.
- Buffers 를 1차 지표로 삼되, 정렬/해시 작업량은 `OMem/1Mem/Used-Mem` 을 함께 본다.
- 병렬은 기본적으로 끈다(`/*+ NO_PARALLEL */`). 병렬을 주제로 한 문제에서만 켠다.
